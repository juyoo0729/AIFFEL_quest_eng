## 2. 각 섹션 체크포인트 답변

### 섹션 1 — 들어가며: 왜 모델을 배포해야 하는가?

**Q1. `.pth` 파일만 전달했을 때, 상대방이 모델을 바로 사용할 수 없는 이유는 무엇입니까?**

`.pth` 파일에는 가중치(숫자 값)만 들어 있고 **모델 구조(클래스 정의), 전처리/후처리 코드, 실행 환경(Python·PyTorch·라이브러리 버전)이 포함되지 않기 때문**입니다. 상대방은 동일한 모델 클래스 코드와 동일한 버전의 환경을 갖추어야만 모델을 복원할 수 있습니다. 즉 모델이 특정 환경에 갇혀 있는 상태입니다.

**Q2. 모델 학습(Training)과 모델 배포(Serving)의 핵심 차이를 한 문장으로 설명할 수 있습니까?**

학습은 데이터를 이용해 **좋은 모델을 만드는 과정**이고, 배포는 그렇게 만든 모델을 **개발자가 아닌 사용자도 안정적으로 사용할 수 있도록 세상에 꺼내놓는 과정**입니다.

**Q3. 모델 배포에서 사용자와 서버가 소통하는 방식은 무엇입니까?**

**HTTP 기반의 API**입니다. 사용자는 약속된 형식(JSON)으로 요청을 보내고, 모델·전처리·후처리를 모두 품은 서버가 약속된 형식으로 응답합니다. 사용자는 Python이나 모델 내부를 몰라도 됩니다.

### 섹션 2 — 환경 세팅: venv와 requirements.txt

**Q1. 가상환경 없이 `pip install`을 하면 패키지가 어디에 설치됩니까? 그것이 왜 문제가 될 수 있습니까?**

**시스템 Python(전역) 환경**에 설치됩니다. 모든 프로젝트가 하나의 패키지 공간을 공유하게 되어, 프로젝트 A가 torch 2.1.0이 필요하고 프로젝트 B가 torch 2.3.0이 필요하면 서로 충돌합니다. 한 프로젝트를 위해 버전을 올리면 다른 프로젝트가 깨질 수 있습니다.

**Q2. `pip freeze`로 생성한 파일과 직접 작성한 `requirements.txt`의 차이는 무엇입니까?**

- `pip freeze`: 하위 의존성까지 **모든 패키지를 정확한 버전(`==`)으로 기록**합니다. 정밀한 환경 재현에 유리하지만 목록이 길어 가독성이 떨어집니다.
- 직접 작성: 사람이 관리하는 **핵심 패키지만** 기록하고, 필요 시 버전 범위를 지정합니다. 읽기 쉽고 의도가 드러나지만 하위 의존성 버전까지는 고정하지 못합니다.

실무에서는 둘을 병행하는 경우가 많습니다 (`requirements.txt` + `requirements_freeze.txt`).

**Q3. 동료에게 프로젝트를 전달할 때, `.venv` 폴더 대신 무엇을 공유해야 합니까?**

**`requirements.txt`** (소스 코드와 함께)를 공유합니다. `.venv`는 용량이 크고 OS에 종속적이라 전달해도 동작하지 않습니다. 동료는 자기 컴퓨터에서 `python -m venv .venv` 후 `pip install -r requirements.txt`로 동일한 환경을 재현합니다.

### 섹션 3 — RESTful API

**Q1. 모델 추론 요청에 GET이 아닌 POST를 사용하는 이유는 무엇입니까?**

추론 입력(텍스트, 픽셀 배열 등)은 크고 구조화된 데이터라 **요청 본문(body)에 담아야 하기 때문**입니다. GET은 본문이 없고 필요한 정보를 URL에 넣어야 하는데, URL은 길이 제한이 있고 복잡한 JSON 구조를 표현하기 어렵습니다. POST는 본문에 제한 없이 JSON 데이터를 담아 "데이터를 보내고 처리 결과를 받는" 의미에도 부합합니다.

**Q2. 상태 코드 `422`는 어떤 상황에서 발생합니까?**

요청은 서버에 도달했지만 **본문의 데이터가 검증 규칙에 맞지 않을 때**(Unprocessable Entity) 발생합니다. 예: 필수 필드 누락, 잘못된 타입, 범위를 벗어난 값. 4xx이므로 서버 잘못이 아니라 **클라이언트의 요청이 잘못된 것**입니다. FastAPI에서는 Pydantic 검증 실패 시 자동으로 422를 반환합니다.

**Q3. `requests.post(url, json=data)`에서 `json=` 파라미터는 내부적으로 어떤 일을 합니까?**

1. Python dict인 `data`를 **JSON 문자열로 자동 직렬화**(`json.dumps`)하여 요청 본문에 담고,
2. 요청 헤더에 **`Content-Type: application/json`을 자동으로 설정**합니다.

`data=` 파라미터와 달리 직렬화와 헤더 설정을 직접 할 필요가 없습니다.

**Q4. Python의 `True`는 JSON에서 어떻게 표현됩니까?**

소문자 **`true`**로 표현됩니다. (마찬가지로 `False` → `false`, `None` → `null`)

### 섹션 4 — 모델 직렬화

**Q1. `state_dict`로 저장한 `.pth` 파일을 불러올 때, 모델 클래스 정의가 필요한 이유는 무엇입니까?**

`.pth` 파일에는 **가중치 텐서들만 딕셔너리 형태로 저장**되고, 레이어들이 어떤 구조로 연결되는지는 저장되지 않기 때문입니다. 가중치를 담을 "그릇"인 모델 구조는 코드(`SimpleClassifier` 클래스)로 먼저 만들어야 하고, 그 위에 `load_state_dict()`로 가중치를 채워 넣는 방식입니다.

**Q2. `torch.jit.trace`와 `torch.jit.script`는 각각 어떤 상황에서 사용합니까?**

- `trace`: 더미 입력을 실제로 통과시켜 연산 경로를 기록합니다. **분기(if/else)가 없는 일반적인 모델**에 적합하며 더 안정적입니다.
- `script`: Python 코드를 직접 분석해 컴파일합니다. **입력에 따라 다른 연산 경로를 타는(동적 제어 흐름이 있는) 모델**에 사용합니다. 단, 지원되지 않는 Python 문법이 있으면 에러가 날 수 있습니다.

**Q3. ONNX의 가장 큰 장점은 무엇이며, 어떤 상황에서 선택해야 합니까?**

가장 큰 장점은 **프레임워크 독립성**입니다. PyTorch로 만든 모델을 TensorFlow 환경, TensorRT/OpenVINO 같은 하드웨어 최적화 엔진, 또는 C++/C#/Java 런타임에서도 실행할 수 있습니다. **추론 속도가 중요한 프로덕션 환경**이나 **PyTorch가 아닌 환경에서 모델을 실행해야 할 때** 선택합니다.

**Q4. `torch.onnx.export()`에서 `dynamic_axes`를 지정하지 않으면 어떤 문제가 생길 수 있습니까?**

내보낼 때 사용한 더미 입력의 크기로 **배치 크기가 고정**됩니다(예: `batch_size=1`). 배포 환경에서 한 번에 여러 입력이 들어오는 배치 추론을 하면 입력 shape 불일치로 실패합니다. `dynamic_axes`로 배치 축을 가변으로 지정해야 임의 크기의 배치를 처리할 수 있습니다.

## 3. 마치며 — Day 1 종합 점검 (Q1~Q10)

**Q1. 모델 학습과 모델 배포의 핵심 차이를 한 문장으로 설명하세요.**

학습은 좋은 모델을 만드는 것이고, 배포는 그 모델을 다른 환경·다른 사람도 사용할 수 있도록 서비스 형태로 꺼내놓는 것입니다.

**Q2. "내 컴퓨터에서는 되는데" 문제의 근본 원인은 무엇입니까?**

**모델이 특정 환경에 갇혀 있기 때문**입니다. 실행 환경(라이브러리·버전), 모델 구조 코드, 전처리 로직이 함께 공유되지 않아, 받는 쪽에서 동일한 조건을 재현할 수 없는 것이 근본 원인입니다.

**Q3. 가상환경을 사용하지 않으면 어떤 문제가 발생할 수 있습니까?**

모든 패키지가 전역에 설치되어 프로젝트 간 버전 충돌이 발생합니다. 한 프로젝트 때문에 버전을 바꾸면 다른 프로젝트가 깨지고, 내 환경에 어떤 패키지가 필요한지 구분할 수 없어 환경 재현도 어려워집니다.

**Q4. pip freeze와 직접 작성한 requirements.txt의 용도 차이는?**

`pip freeze`는 하위 의존성까지 전부 고정한 **정밀 재현용** 목록이고, 직접 작성한 `requirements.txt`는 핵심 패키지만 담은 **사람이 관리하는** 목록입니다.

**Q5. 모델 추론 요청에 POST를 사용하는 이유는?**

추론 입력은 크고 구조화된 JSON 데이터라 요청 본문에 담아야 하는데, 본문을 가지는 메서드가 POST이기 때문입니다.

**Q6. 상태 코드 200, 400, 500은 각각 어떤 상황을 의미합니까?**

- **200 (OK)**: 요청이 정상적으로 처리됨 (성공)
- **400 (Bad Request)**: 클라이언트의 요청 자체가 잘못됨 (클라이언트 잘못)
- **500 (Internal Server Error)**: 요청 처리 중 서버 내부에서 예기치 못한 에러 발생 (서버 잘못)

**Q7. state_dict 방식은 왜 모델 클래스 정의가 필요합니까?**

가중치만 저장되고 모델 구조는 저장되지 않으므로, 구조를 코드로 먼저 만든 뒤 가중치를 채워야 하기 때문입니다.

**Q8. ONNX의 가장 큰 장점과, 사용해야 할 시점은?**

프레임워크 독립성이 가장 큰 장점이며, 추론 성능 최적화가 필요하거나 PyTorch 외의 런타임(TensorRT, C++ 등)에서 모델을 실행해야 할 때 사용합니다.

**Q9. 모델 저장 전에 model.eval()을 호출해야 하는 이유는?**

Dropout, BatchNorm 등의 레이어는 학습 모드와 추론 모드에서 동작이 다르기 때문입니다. train 모드인 채로 저장/변환(특히 TorchScript trace)하면 Dropout이 활성화된 상태가 기록되어, 배포 후 추론 결과가 매번 달라지거나 원본과 일치하지 않게 됩니다.

**Q10. predict() 함수를 별도 모듈로 분리한 이유는 무엇입니까?**

이후 FastAPI 서버가 **`from app.model_utils import load_model, predict`로 그대로 import해서 사용**할 수 있게 하기 위해서입니다. 추론 로직을 노트북에서 분리해 두면 API 코드와 모델 코드의 역할이 나뉘어 재사용·테스트·유지보수가 쉬워지고, 노트북 없이도 서버가 독립적으로 동작합니다.
