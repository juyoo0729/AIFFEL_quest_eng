### ✅ 체크포인트

1. Day 5(정형 데이터)와 Day 7(텍스트 생성)에서 전처리가 어떻게 다릅니까?
정형 데이터(Day 5)는 숫자·범주형 값이라 결측치 채우기, 스케일링(정규화/표준화), 원-핫 인코딩, 이상치 제거 같은 처리를 해. 입력이 이미 표 형태로 정리돼 있어서 "값을 모델이 먹기 좋게 다듬는" 작업이 중심이야.반면 텍스트 생성(Day 7)은 비정형 텍스트라 토크나이징이 핵심이야. 문장을 토큰 단위로 쪼개고 → 각 토큰을 정수 ID로 변환(인코딩)하고 → 모델 최대 길이에 맞춰 자르거나 패딩하는 과정이 들어가. 그리고 생성 결과는 다시 토큰 ID에서 텍스트로 되돌리는 디코딩까지 필요해. 정형 데이터엔 없는 단계야.한 줄 요약: 정형은 "수치 가공(스케일링·인코딩)", 텍스트는 "토큰 변환(토크나이징·디코딩)"이 중심이고, 텍스트는 입력→출력 양방향 변환이 다 필요하다는 게 차이야.
2. Hugging Face Transformers 라이브러리의 역할은 무엇입니까?
사전학습된 모델과 토크나이저를 from_pretrained() 한 줄로 불러와서 바로 쓸 수 있게 해주는 라이브러리야. 모델 구조를 직접 구현하거나 가중치를 수동으로 받을 필요 없이, 모델 이름만 지정하면 Hugging Face Hub에서 자동으로 다운로드·로드해줘.
핵심 역할 세 가지로 보면: 토크나이저로 텍스트↔토큰 변환을 처리하고, 모델 클래스(GPT2LMHeadModel 등)로 추론을 돌리고, model.generate()로 텍스트 생성을 표준화된 인터페이스로 제공해. 덕분에 모델이 GPT2든 BERT든 같은 패턴으로 다룰 수 있어서, 이 노트북처럼 "모델을 API로 서빙하는" 데 집중할 수 있게 해주는 게 핵심이야.

### 2.4 멀티턴 대화 테스트

멀티턴 챗봇의 핵심은 **이전 대화를 프롬프트에 포함**하는 것입니다.
RAG/Agent에서 경험하셨을 패턴과 동일합니다.

```python
# 대화 기록을 하나의 프롬프트로 결합
conversation = [
    "사용자: 안녕하세요!",
    "봇: 안녕하세요! 무엇을 도와드릴까요?",
    "사용자: 오늘 날씨가 어때?",
]

prompt = "\n".join(conversation) + "\n봇:"        # *your code* — 대화 기록 결합

input_ids = tokenizer.encode(prompt, return_tensors="pt").to(device)

with torch.no_grad():
    output_ids = model.generate(
        input_ids, max_new_tokens=50, temperature=0.8,
        top_k=50, do_sample=True, pad_token_id=tokenizer.eos_token_id,
    )

full_response = tokenizer.decode(output_ids[0], skip_special_tokens=True)
bot_response = full_response[len(prompt):].split("사용자:")[0].strip()

print(f"봇 응답: {bot_response}")
```

### ✅ 체크포인트

1. 토크나이저의 `encode()`와 `decode()`는 각각 어떤 변환을 수행합니까?
encode()와 decode()의 변환
encode()는 텍스트 → 정수 토큰 ID로 바꾸는 변환이야. 사람이 읽는 문장("인공지능의 미래는")을 모델이 처리할 수 있는 숫자 배열로 만들어줘. decode()는 그 반대로, 모델이 출력한 토큰 ID 배열을 다시 사람이 읽을 수 있는 텍스트로 되돌리는 변환입니다
한 줄로: encode는 입력 단계(텍스트→숫자), decode는 출력 단계(숫자→텍스트). 모델은 숫자만 다루기 때문에 입력 들어갈 때와 결과 나올 때 이 두 변환이 짝으로 필요해.
2. `model.generate()`의 `temperature` 파라미터는 생성 결과에 어떤 영향을 줍니까?
temperature는 생성 결과의 **다양성(무작위성)**을 조절하는 값이야. 모델이 다음 토큰을 고를 때 확률 분포를 얼마나 평평하게/뾰족하게 만들지를 결정합니다

낮으면(예: 0.2) → 확률 높은 토큰에 집중 → 안정적이고 일관되지만 단조롭고 반복적인 결과
높으면(예: 1.2) → 확률 분포가 평평해져 덜 likely한 토큰도 잘 뽑힘 → 창의적·다양하지만 엉뚱하거나 문맥 벗어난 결과가 늘어남
3. 멀티턴 대화에서 이전 대화 기록을 프롬프트에 포함하는 이유는 무엇입니까?
GPT 같은 언어 모델은 상태(state)를 기억하지 않기 때문이야. 각 요청은 독립적으로 처리돼서, 모델 자체는 바로 직전에 무슨 대화를 했는지 전혀 몰라. "아까 말한 그거" 같은 맥락을 이해하려면, 이전 대화를 매번 프롬프트에 같이 넣어줘서 모델이 전체 흐름을 한 번에 보게 해야합니다

### 3.1 추론 모듈 작성

```python
%%writefile app/chatbot_model.py
"""
Day 7 - 한국어 GPT 챗봇 모델
"""
import torch
from transformers import PreTrainedTokenizerFast, GPT2LMHeadModel


class ChatbotModel:
    """Hugging Face 한국어 GPT 모델을 로드하고 텍스트를 생성합니다."""

    def __init__(self, model_name: str = "skt/kogpt2-base-v2"):
        self.device = "cuda" if torch.cuda.is_available() else "cpu"

        self.tokenizer = PreTrainedTokenizerFast.from_pretrained(model_name)
        self.model = GPT2LMHeadModel.from_pretrained(model_name, use_safetensors=True, torch_dtype=torch.float16)
        self.model = self.model.to(self.device)
        self.model.eval()

        self.model_name = model_name

    def generate_response(
        self,
        messages: list[dict],
        max_new_tokens: int = 100,
        temperature: float = 0.8,
        top_k: int = 50,
        top_p: float = 0.9,
    ) -> str:
        """
        대화 기록을 받아 응답을 생성합니다.

        Args:
            messages: [{"role": "user", "content": "안녕"}, {"role": "bot", "content": "안녕하세요!"}, ...]
            max_new_tokens: 최대 생성 토큰 수
            temperature: 생성 다양성
        Returns:
            생성된 응답 텍스트
        """
        # 대화 기록 → 프롬프트 구성
        prompt = self._build_prompt(messages)              # *your code* — 프롬프트 구성

        # 토크나이징
        input_ids = self.tokenizer.encode(
            prompt, return_tensors="pt"
        ).to(self.device)

        # 토큰 수 제한 (모델 최대 길이 초과 방지)
        max_length = getattr(self.model.config, "n_positions", 1024)
        if input_ids.shape[1] > max_length - max_new_tokens:
            # 최근 대화만 유지
            input_ids = input_ids[:, -(max_length - max_new_tokens):]

        # 텍스트 생성
        with torch.no_grad():
            output_ids = self.model.generate(
                input_ids,
                max_new_tokens=max_new_tokens,             # *your code* — 생성 파라미터
                temperature=temperature,
                top_k=top_k,
                top_p=top_p,
                do_sample=True,
                pad_token_id=self.tokenizer.eos_token_id,
            )

        # 디코딩: 생성된 부분만 추출
        full_text = self.tokenizer.decode(output_ids[0], skip_special_tokens=True)
        response = full_text[len(prompt):].strip()

        # "사용자:" 이후 텍스트가 나오면 거기까지만 자름
        if "사용자:" in response:
            response = response.split("사용자:")[0].strip()

        return response if response else "(응답을 생성하지 못했습니다)"

    def _build_prompt(self, messages: list[dict]) -> str:
        """대화 기록을 프롬프트 문자열로 변환합니다."""
        lines = []
        for msg in messages:
            role = "사용자" if msg["role"] == "user" else "봇"
            lines.append(f"{role}: {msg['content']}")
        lines.append("봇:")  # 모델이 이어서 생성하도록
        return "\n".join(lines)
```

```python
%%writefile app/chatbot_schemas.py
"""
Day 7 - 챗봇 API 스키마
"""
from pydantic import BaseModel, Field
from typing import Optional


class Message(BaseModel):
    """단일 대화 메시지"""
    role: str = Field(..., description="역할: 'user' 또는 'bot'")
    content: str = Field(..., min_length=1, description="메시지 내용")


class ChatRequest(BaseModel):
    """챗봇 요청"""
    messages: list[Message] = Field(
        ...,
        min_length=1,
```

### ✅ 체크포인트

1. `ChatRequest`의 `messages`가 리스트인 이유는 무엇입니까?
멀티턴 대화는 여러 발화가 순서대로 누적되는 구조이기 때문입니다. 사용자와 봇이 주고받은 대화가 시간 순으로 쌓이므로, 이를 담기 위해서는 순서가 있는 리스트가 적합합니다. 각 원소는 {"role": "user", "content": "..."} 형태로 누가 한 말인지(role)와 그 내용(content)을 담고, 리스트 전체가 대화의 흐름을 표현합니다. 만약 단일 문자열이었다면 역할 구분과 대화 순서를 표현할 수 없으므로, 리스트 형태를 사용하여 대화 기록 전체를 구조적으로 주고받습니다
2. 서버가 대화 기록을 저장하지 않고, 클라이언트가 매번 전체 기록을 보내는 이유는?
무상태(stateless) 설계를 적용하기 위해서입니다. 서버가 각 사용자의 대화를 기억하지 않도록 만들면 다음과 같은 이점이 있습니다. 첫째, 확장성 측면에서 서버가 상태를 가지지 않으므로 요청이 어느 서버 인스턴스로 전달되든 동일하게 처리되며, 서버를 여러 대로 늘리거나(로드 밸런싱) 재시작해도 대화가 끊기지 않습니다. 둘째, 단순성 측면에서 서버가 세션마다 대화를 저장하고 관리할 필요가 없어 메모리 관리나 세션 만료 처리 같은 복잡한 로직이 사라집니다. 셋째, 각 요청이 자기 완결적이므로 한 요청의 실패가 다른 요청에 영향을 주지 않습니다. 대신 클라이언트가 대화 맥락을 책임지고 매번 전체 기록을 전송하며, 이는 REST API의 기본 철학(stateless)과도 부합합니다.
3. `max_new_tokens`을 너무 크게 설정하면 어떤 문제가 발생할 수 있습니까?
여러 문제가 발생할 수 있습니다. 첫째, 토큰을 하나씩 순차적으로 생성하기 때문에 최대 토큰 수가 커지면 응답 시간이 그만큼 길어지고, API가 느려지며 타임아웃의 위험이 생깁니다. 둘째, 시퀀스가 길어질수록 GPU/CPU 메모리 사용량이 늘어나 심한 경우 메모리 부족(OOM)이 발생할 수 있습니다. 셋째, 입력 토큰과 생성 토큰의 합이 모델의 최대 컨텍스트 길이(예: GPT2는 1024)를 초과하면 오류가 나거나 앞부분이 잘릴 수 있습니다(본 프로젝트 코드에 max_length - max_new_tokens 체크 로직이 있는 이유입니다). 넷째, 필요 이상으로 길게 생성하면 같은 말을 반복하거나 주제에서 벗어나는 등 품질이 저하될 수 있습니다. 따라서 용도에 맞게 적절한 값(챗봇의 경우 100~200 정도)으로 설정하는 것이 좋습니다.

### ✅ 체크포인트

1. `st.chat_message`와 `st.chat_input`은 각각 어떤 역할을 합니까?
st.chat_message는 채팅 메시지를 화면에 표시하는 컨테이너 역할을 합니다. role(예: "user", "assistant")을 지정하면 그에 맞는 말풍선 형태와 아이콘으로 메시지를 렌더링하여, 누가 한 말인지 시각적으로 구분되는 채팅 인터페이스를 만들어 줍니다.
st.chat_input은 화면 하단에 고정된 채팅 입력창을 제공하는 역할을 합니다. 사용자가 텍스트를 입력하고 전송하면 그 값을 반환하며, 이를 받아 대화 처리 로직으로 넘기게 됩니다. 정리하면 st.chat_message는 출력(메시지 표시), st.chat_input은 입력(사용자 입력 수집)을 담당합니다.
2. `st.session_state["chat_messages"]`에 대화 기록을 저장하는 이유는?
Streamlit은 사용자가 입력하거나 버튼을 누르는 등 상호작용이 일어날 때마다 스크립트 전체를 처음부터 다시 실행하기 때문입니다. 이때 일반 변수는 매 실행마다 초기화되어 사라지므로, 그냥 변수에 대화를 담으면 이전 대화가 유지되지 않습니다.
st.session_state는 이러한 재실행 사이에서도 값을 유지해 주는 저장 공간입니다. 여기에 대화 기록을 저장하면 화면이 다시 그려져도 이전 대화가 보존되어, 멀티턴 대화를 이어갈 수 있고 누적된 기록을 서버로 함께 전송할 수도 있습니다.
3. "대화 초기화" 버튼이 `st.rerun()`을 호출하는 이유는 무엇입니까?
변경된 상태를 즉시 화면에 반영하기 위해서입니다. 버튼을 눌러 st.session_state의 대화 기록을 비우더라도, 그 변경 사항은 다음 번 스크립트 실행 때 화면에 적용됩니다. st.rerun()을 호출하면 스크립트를 곧바로 처음부터 다시 실행시켜, 비워진 대화 기록이 바로 화면에 반영되어 채팅창이 즉시 초기화된 모습으로 보이게 됩니다. 이 호출이 없으면 기록은 비워졌어도 화면은 다음 상호작용이 일어날 때까지 갱신되지 않을 수 있습니다.

```python
from concurrent.futures import ThreadPoolExecutor, as_completed

def send_chat(i):
    start = time.time()
    resp = requests.post(f"{API_BASE}/chat",
        json={"messages": [{"role": "user", "content": f"질문 {i}번입니다"}], "max_new_tokens": 30},
        headers={"X-API-Key": VALID_KEY}, timeout=60)
    return {"id": i+1, "elapsed": round(time.time()-start, 1), "status": resp.status_code}

print("\n[테스트 4] 동시 요청 (4개)")
start = time.time()
with ThreadPoolExecutor(max_workers=4) as ex:
    futures = [ex.submit(send_chat, i) for i in range(4)]
    results = [f.result() for f in as_completed(futures)]

total = round(time.time() - start, 1)
for r in sorted(results, key=lambda x: x["id"]):
    print(f"  요청 #{r['id']}: {r['elapsed']}초 (HTTP {r['status']})")
print(f"  전체: {total}초")
```

```
Q1. Day 5(정형 데이터)와 Day 7(텍스트 생성)에서 전처리 방식의 차이는?
정형 데이터(Day 5)는 숫자·범주형 값으로 이루어져 있어 결측치 처리, 스케일링(정규화/표준화), 원-핫 인코딩, 이상치 제거 등 값을 모델이 학습하기 좋게 다듬는 작업이 중심입니다. 반면 텍스트 생성(Day 7)은 비정형 텍스트를 다루므로 토크나이징이 핵심으로, 문장을 토큰으로 나누고 정수 ID로 변환(인코딩)한 뒤 생성 결과를 다시 텍스트로 되돌리는 디코딩까지 필요합니다. 정리하면 정형은 수치 가공이 중심이고, 텍스트는 토큰 변환(인코딩·디
Q2. 멀티턴 대화에서 서버가 상태를 유지하지 않는 이유는?
무상태(stateless) 설계를 적용하기 위해서입니다. 서버가 각 사용자의 대화를 기억하지 않으면, 요청이 어느 서버 인스턴스로 전달되든 동일하게 처리되어 서버를 여러 대로 늘리거나 재시작해도 대화가 끊기지 않습니다(확장성). 또한 세션마다 대화를 저장·관리할 필요가 없어 로직이 단순해지고, 각 요청이 자기 완결적이라 한 요청의 실패가 다른 요청에 영향을 주지 않습니다. 대신 대화 기록은 클라이언트가 보관했다가 매번 전체를 함께 전송하며, 이는 REST API의 기본 철학과도 부합합니다.
Q3. API Key가 잘못되면 서버는 어떤 상태 코드를 반환하고, UI는 어떻게 처리합니까?
서버는 인증 실패를 의미하는 401 Unauthorized 상태 코드를 반환합니다(키 자체는 있으나 권한이 없는 경우라면 403 Forbidden을 쓰기도 합니다). UI(Streamlit) 측에서는 응답의 상태 코드를 확인하여, 401이 돌아오면 정상 응답으로 처리하지 않고 "API Key가 올바르지 않습니다"와 같은 오류 메시지를 사용자에게 보여줍니다. 즉 잘못된 키로 받은 응답을 챗봇 답변인 것처럼 표시하지 않고, 인증 오류임을 구분해 안내하는 방식으로 처리합니다.
Q4. temperature를 낮추면 생성 결과에 어떤 변화가 있습니까?
temperature를 낮추면 다음 토큰을 선택할 때 확률이 높은 토큰에 더 집중하게 되어, 생성 결과가 더 안정적이고 일관되며 예측 가능해집니다. 같은 입력에 대해 비슷한 결과가 나올 가능성이 높아지는 대신, 표현이 단조롭거나 반복적으로 흐를 수 있습니다. 반대로 높이면 다양하고 창의적이지만 엉뚱한 결과가 늘어나므로, 낮은 temperature는 정확성·일관성이 중요한 상황에 적합합니다.
Q5. 이 서비스를 다른 컴퓨터에서 실행하려면 무엇이 필요합니까?
먼저 동일한 실행 환경이 필요합니다. Python과 함께 프로젝트가 사용하는 라이브러리(transformers, torch, fastapi, uvicorn, streamlit 등)를 requirements.txt 기준으로 설치해야 합니다. 다음으로 프로젝트 코드 전체(app/, frontend/ 폴더의 소스 파일들)가 있어야 하고, 모델은 최초 실행 시 Hugging Face Hub에서 자동으로 다운로드되므로 인터넷 연결이 필요합니다. 또한 API Key 같은 인증 정보(환경 변수나 설정 값)를 동일하게 맞춰야 하며, FastAPI 서버와 Streamlit이 사용하는 포트가 열려 있어야 합니다. 큰 모델을 GPU로 돌리려면 해당 컴퓨터에 GPU와 맞는 버전의 torch(CUDA 대응)도 갖춰져 있어야 합니다.
```

## 🪪 프로젝트 회고

> Day 7 — 트랜스포머 챗봇 서비스를 만들면서 느낀 점과 배운 점을 정리합니다.

### 1. 이번 프로젝트에서 한 일

이번에는 Day 5의 정형 데이터 회귀 서비스와 달리, **텍스트를 입력받아 텍스트를 생성하는** 한국어 GPT 챗봇 서비스를 처음부터 끝까지 만들었습니다. 구조는 지난 프로젝트와 같은 **프론트엔드(Streamlit) ↔ 백엔드(FastAPI) 분리 아키텍처**였지만, 다루는 데이터가 숫자에서 자연어로 바뀌면서 새로 신경 쓸 부분이 많았습니다.

- `chatbot_model.py` — Hugging Face 모델 로드 + 토크나이징 → 생성 → 디코딩
- `chatbot_schemas.py` — Pydantic으로 요청/응답 형식과 입력 범위(temperature, max_new_tokens) 검증
- `chatbot_api.py` — 인증 → 추론 → 응답을 묶은 FastAPI 서버
- `frontend/app_chatbot.py` — `st.chat_message` / `st.chat_input` 기반 대화형 UI

### 2. 새롭게 이해한 것

- **전처리의 의미가 데이터마다 다르다.** Day 5에서는 정규화·스케일링이 전처리였는데, 텍스트에서는 **토크나이징(인코딩) → 생성 → 디코딩**이 전처리·후처리의 핵심이라는 걸 코드로 직접 확인했습니다.
- **멀티턴은 서버가 기억하는 게 아니다.** 처음에는 서버가 대화를 기억하는 줄 알았는데, 실제로는 **클라이언트가 대화 기록 전체를 매 요청마다 다시 보내는** 무상태(stateless) 구조였습니다. 그래야 서버를 늘리거나 재시작해도 대화가 끊기지 않는다는 점이 인상 깊었습니다.
- **동기/비동기의 차이가 체감됐다.** 추론처럼 시간이 걸리는 작업을 `async def` 안에서 그냥 돌리면 이벤트 루프가 막힌다는 것을, `run_in_executor`로 스레드풀에 넘기는 코드를 보며 이해했습니다.

### 3. 막혔던 점과 해결 (가장 기억에 남는 부분)

서버를 띄우고 `/chat`에 요청을 보냈더니 **`ReadTimeout: read timeout=60`** 에러가 났습니다. 처음에는 모델 추론이 느려서 그런 줄 알았는데, 직접 시간을 재보니 모델 로드는 약 7초, 생성은 30토큰 기준 1~2초로 **추론 자체는 빠르다**는 걸 확인했습니다.

원인은 추론 속도가 아니라 **타이밍**이었습니다. 모델은 FastAPI의 `startup` 이벤트에서 로드되는데, 로드가 끝나기 전에는 서버가 연결만 받고 응답은 못 합니다. 그런데 서버 시작 셀이 `time.sleep(10)`으로 무작정 10초만 기다리고 다음으로 넘어가다 보니, **모델이 아직 로드 중인 상태에서 요청이 날아가 60초 동안 멈췄던** 것이었습니다.

그래서 `time.sleep(10)`을 **`/health`가 `"healthy"`가 될 때까지 폴링하는 코드**로 바꿔서, 모델이 실제로 준비된 뒤에만 다음 셀로 넘어가도록 고쳤습니다. 이 과정에서 "에러 메시지를 그대로 믿지 말고, 먼저 어디서 시간이 새는지 직접 측정해 보자"는 걸 배웠습니다.

### 4. 아쉬운 점 / 더 해보고 싶은 것

- 모델이 작다 보니(kogpt2 계열) 응답 품질이 들쭉날쭉했습니다. 더 큰 모델이나 파인튜닝을 적용하면 어떻게 달라질지 궁금합니다.
- 지금은 API Key가 코드에 들어 있는데, 환경 변수나 별도 비밀 관리로 분리하는 방법을 다음에 적용해 보고 싶습니다.
- 대화가 길어지면 토큰 길이를 잘라내는 부분이 있는데, 더 똑똑하게 맥락을 유지하는 방법(요약 등)도 시도해 보고 싶습니다.

### 5. 한 줄 정리

> 모델을 "돌리는" 것과 "서비스로 띄우는" 것은 다른 일이고, 그 사이에는 **인증·검증·비동기·로딩 타이밍** 같은 현실적인 문제들이 있다는 걸 직접 부딪히며 배운 프로젝트였습니다.
